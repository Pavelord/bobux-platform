# Участие в разработке Bobux

Перед началом прочитайте [обзор](README.md), [настройку окружения](docs/DEVELOPMENT.md) и актуальный отчёт по затрагиваемой системе в `docs/`.

## Сообщение об ошибке

В [issue](https://github.com/Pavelord/bobux-platform/issues) укажите:

- Версию клиента или commit, платформу, модель телефона / характеристики ПК.
- Режим и короткие шаги воспроизведения; ожидаемый и фактический результат.
- Частоту ошибки и, если возможно, короткую запись экрана.
- Подходящий фрагмент лога без паролей, cookies, токенов и персональных данных.

Для проблем с производительностью полезнее время входа в конкретный режим, FPS и описание устройства, чем общее «лагает». Для ошибки Luau приложите минимальный собственный скрипт, воспроизводящий проблему.

## Изменения кода

1. Создайте отдельную ветку и ограничьте изменение одной понятной задачей.
2. Сначала найдите существующий маршрут данных и подходящую проверку. Не создавайте второй независимый владелец персонажа, инвентаря или сетевого состояния.
3. Сохраняйте совместимость опубликованных миров и Luau-скриптов. Изменение протокола требует явного поведения для старых и новых клиентов / серверов.
4. Выполните проверки затронутой системы и опишите результат в pull request.

В описании PR объясните, какая проблема исправлена, что теперь происходит и как это проверено. Если Android, сеть или конкретный режим не проверялись, укажите это прямо. Не представляйте успешную проверку синтаксиса как доказательство исправления игрового сценария.

В GDScript используйте принятые в соседнем коде типы и стиль. Общие runtime-правила персонажа должны одинаково работать у игрока и NPC. Устранение задержек не должно отключать скрипты или незаметно менять поведение миров.

## Работа над Roblox API и персонажем

Совместимость строится по [плану A–J](docs/ROBLOX_CHARACTER_ARCHITECTURE_RU.md). У API должны быть понятные источник поведения, область поддержки и ограничения.

- Используйте официальную документацию и собственные наблюдения в официальной Roblox Studio.
- Не добавляйте утекшие или декомпилированные исходники, чужие анимационные ключи и ассеты без права на распространение.
- Разделяйте native-наблюдение, реализацию Bobux и проверку их соответствия.
- Сохраняйте исходные результаты, hashes, версии окружения и заранее заданные допуски. Не переписывайте старый FAIL в PASS и не подгоняйте допуск по holdout.
- Отсутствие измерения отмечайте явно. Stub, metadata setter или существующий класс ещё не доказывают работу физики, рендера или сетевой репликации.

Для текущей character parity задачи защищены `scripts/place_editor/studio.gd`, `scripts/main/main.gd`, `addons/rbxl_importer/rbxl_runtime_importer.gd` и файлы `map_format.gd`. Изменение их в рамках этой задачи требует отдельного пересмотра её scope; не обходите baseline-проверку широким списком исключений.

## Что хранить в Git

Добавляйте исходники, сцены, необходимые ресурсы, повторяемые проверки и полезную документацию. Крупные авторские модели и миры размещаются через действующие правила Git LFS.

Не добавляйте `.godot/`, локальные toolchains, `node_modules/`, промежуточные экспорты, кэши загрузок, приватные базы и секреты. Для измерений сохраняйте только материалы, необходимые для воспроизводимости; упаковка доказательств должна проверять точное восстановление исходных байтов.

Для стороннего кода или ассета укажите происхождение, лицензию и необходимые notices. Отсутствие общей лицензии Bobux нельзя заменять самостоятельно выбранной лицензией в отдельном PR.

## Проверка и выпуск

Команды приведены в [DEVELOPMENT.md](docs/DEVELOPMENT.md). Полный character runner запускается последовательно и требует закрытой Roblox Studio, чтобы измерения и Godot-проверки не мешали друг другу.

Публикация исходников в GitHub и выпуск игрового обновления — разные операции. Экспорт, загрузка сборок, изменение launcher manifest и развёртывание сервисов выполняются только в рамках согласованного выпуска.
